# Linux HTTP p99 implementation plan

Goal: reduce default Linux HTTP tail latency without materially sacrificing throughput or correctness.

Architecture: retain the existing epoll and io_uring implementations. Compare their behavior on the same binary and host before changing default dispatch or bounded busy waiting. Keep explicit backend overrides available. No CPU pinning, benchmark response special cases or semantic shortcuts in the default runtime.

Evidence: the historical binary's three-round diagnostic gives default / epoll / io_uring median p99 of 2.35 / 1.67 / 1.06 ms, with 72,005 / 71,665 / 65,844 req/s. Smaller young generation did not improve the default result. This supports investigating mixed I/O scheduling rather than assuming a GC problem; current-version confirmation is still required.

- [x] Start v0.0.1 release at the previously validated public commit; keep later experiments outside that tag.
- [x] Build and upload the current Linux binary, verifying SHA-256.
- [x] Confirm the default versus backend diagnostics with the current binary (`bench/hello_node.mjs`). Preserve raw wrk output and per-process scheduling counters.
- [x] Select the smallest supported change in `crates/kestrel-engine/src/uring.rs` / `fastpath.rs`; evaluate alternatives separately. Candidate A: default epoll, retaining opt-in io_uring. Candidate B: bound the io_uring busy wait more tightly so mixed epoll connections are not delayed. Reject a change if it merely trades substantial throughput for p99.
- [x] Alternate baseline/candidate/Bun/Node for six rounds at 64 connections; verify native HTTP and low/high concurrency as well. Do not combine measurements from different conditions or binaries.
- [x] Run Linux compatibility and real-socket backpressure checks, including explicit backend overrides affected by a change. Verify macOS where shared code changes.
- [x] Review the final diff and record accepted/rejected experiments, version hashes, raw samples and limitations in `docs/performance/2026-10-18-linux-p99/`.
- [x] Publish v0.0.1 only after four release builds, archive checksums and attached assets are verified.

Outcome: default epoll accepted with explicit workload caveats. Repeated 64-connection tests improve p99, and 4096 connections improve both p99 and throughput. At 256 connections epoll is inconsistent; pure io_uring is an opt-in alternative. No universal throughput or tail-latency claim. v0.0.1 published with all four platform archives verified; the optimization is a later source change.
